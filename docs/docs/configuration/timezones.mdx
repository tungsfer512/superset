# Timezones

## Displaying UTC data in a fixed timezone

If your data is stored in UTC and you want charts to group, filter and label it
in a single fixed timezone, set `DISPLAY_TIME_ZONE` to an
[IANA timezone name](https://en.wikipedia.org/wiki/List_of_tz_database_time_zones):

```python
# superset_config.py
DISPLAY_TIME_ZONE = "Asia/Ho_Chi_Minh"
```

### Zone names

The name travels into the generated SQL verbatim, so it has to be one the
target database recognizes. Databases ship the *canonical* IANA zones only,
while Python's tzdata also carries the deprecated `backward` links — PostgreSQL
answers `time zone "Greenwich" not recognized` for those.

Superset resolves a deprecated name to its canonical one before building the
query (`Greenwich` → `Etc/GMT`, `Asia/Saigon` → `Asia/Ho_Chi_Minh`,
`US/Eastern` → `America/New_York`), so a value stored by an older version, or
sent by an embedding host, keeps working. The mapping is read from the zone
database's own `tzdata.zi`, so it follows tzdata updates.

The user-facing picker offers only canonical, region-based zones plus `UTC`. It
deliberately leaves out the region-less legacy zones (`EST`, `CET`, `PST8PDT`,
…): those name a UTC offset rather than a place, which is not what a display
timezone should mean.

Superset then converts temporal columns to wall-clock time in that zone **in
SQL**, before the time grain is applied — so a "day" is a day in that zone, not
in UTC. Time-range filters are compared against the same converted expression,
and relative ranges (`today`, `now`, `Last week`) are resolved in that zone
too, so the filter, the grouping and the axis labels all agree. Values reach
the browser as naive local wall clock, which is how the frontend already
renders them, so no client-side setting is involved.

### Requirements and caveats

- **The data must actually be UTC.** Columns that already hold local time are
  shifted a second time. Opt those out (see below).
- **Engine support.** See the table below. Most engines convert by zone *name*
  and so track DST correctly; a few have no time zone database and shift by a
  fixed offset instead. Engines with no template at all log a warning and are
  left unconverted.
- **Indexes.** Filters are applied to the converted expression, so an index on
  the raw column no longer applies. Add an expression index, e.g. for
  PostgreSQL: `CREATE INDEX ... ON t ((ts AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Ho_Chi_Minh'))`.
- **SQL Lab is not converted** — it runs the SQL you type, unchanged.
- **Legacy "Hours offset"**: a dataset with a non-zero hours offset shifts the
  result in Python on top of this conversion. Clear it before enabling this.
- **Date-only columns** (`DATE`) and columns Superset parses from strings via
  `python_date_format` are never converted; there is no time-of-day to carry
  the offset.

### Per-user timezone

Each user can pick their own timezone from **Settings → Info → Edit user →
Display timezone**. Leaving it on *Instance default* falls back to the value
resolved below. The choice is stored on `user_attribute.display_time_zone` and
is also available over the API:

```bash
curl -X PUT /api/v1/me/ -d '{"display_time_zone": "Asia/Ho_Chi_Minh"}'
curl -X PUT /api/v1/me/ -d '{"display_time_zone": ""}'   # back to the default
```

The resolved timezone is part of the query cache key, so two users in different
timezones never see each other's cached results — at the cost of one cached
copy per timezone actually in use.

A user preference only chooses *which* zone to render in. It cannot switch
conversion **on**: if `DISPLAY_TIME_ZONE` is unset, or the target database has
opted out, nothing is converted regardless of what the user picked. That data
may not be UTC at all, and a preference must not be able to corrupt it.

Where there is no user — Celery tasks, anonymous browsing, embedded dashboards
authenticated by a guest token — the configured default applies. Concretely:

- **Alerts & reports** render in the report executor's timezone, the same user
  whose RLS rules apply.
- **Thumbnails** render in the thumbnail executor's timezone. When
  `THUMBNAIL_EXECUTORS` is `CURRENT_USER` the executor is already part of the
  thumbnail digest, so per-user images stay separate; with a fixed executor
  everyone shares one image, rendered in that account's timezone.
- **Cache warm-up** warms the default-timezone copy. Users with a custom
  timezone simply start from a cold cache.

### Engine support

Verified by running Superset's own generated SQL against a live server and
comparing every result with Python's `zoneinfo` — see
[`scripts/tz-test/`](https://github.com/apache/superset/tree/master/scripts/tz-test).
"Zones correct" is the count out of the 436 the picker offers, checked at one
instant in each hemisphere's summer so that a one-sided DST error still shows.

| Engine | Converts by | Zones correct | Verified against |
|---|---|---|---|
| PostgreSQL | name | 436 / 436 | PostgreSQL 16 |
| MySQL | name, offset fallback | 436 / 436 | MySQL 8 |
| Trino | name | 436 / 436 | Trino 483 |
| ClickHouse | name | 434 / 436 | ClickHouse 24.10 |
| SQLite | offset | 315 / 436 | bundled |
| StarRocks | name, offset fallback | not measured | inherits MySQL |
| Redshift | name | not measured | |
| BigQuery, Snowflake, Hive/Spark, Databricks | name | not measured | |
| Microsoft SQL Server, Presto | offset | not measured | |

Notes on the two engines that are not perfect:

- **SQLite** has no time zone database, so it can only shift by a fixed offset,
  computed when the query is built. The 315 zones that do not observe DST are
  always right; the other 121 are off by the DST amount outside the current
  season. This mostly affects Superset's own example database.
- **ClickHouse 24.10** bundles an older tzdata than Superset's, and so does not
  know `America/Coyhaique` (added in tzdata 2025a). It raises an error rather
  than returning a wrong answer. Any engine can fall behind this way; run the
  checker after upgrading either side.

To check an engine that is not listed — including a cloud warehouse — point the
script at it:

```bash
docker compose exec superset \
  python scripts/tz-test/check_engine_timezones.py "<sqlalchemy-uri>" --all
```

### Overrides

Per database, in the database's **Extra**:

```json
{ "display_time_zone": "UTC" }
```

Use `null` instead of a name to opt the database out entirely.

Per column, in the column's **Extra** — useful for a calculated column that
already converts the timezone itself:

```json
{ "skip_time_zone_conversion": true }
```

### Embedded dashboards

An embedded dashboard runs in a cross-origin iframe, where cookies are
unreliable and the viewer is an ephemeral guest user with no stored preference.
The host application therefore states the zone explicitly, as a URL parameter
alongside `lang`:

```js
embedDashboard({
  id: '...',
  supersetDomain: 'https://superset.example.com',
  mountPoint: document.getElementById('dashboard'),
  fetchGuestToken: () => fetchGuestTokenFromBackend(),
  dashboardUiConfig: {
    urlParams: { lang: 'vi', timezone: 'Asia/Ho_Chi_Minh' },
  },
});
```

Superset validates the value, and the embedded page forwards it as the
`X-Superset-Display-Timezone` header on every API call it makes — the chart data
requests carry no URL parameters of their own. The header name is configurable
via `DISPLAY_TIME_ZONE_HEADER_NAME`, and any client may send it directly:

```
X-Superset-Display-Timezone: Asia/Ho_Chi_Minh
```

The underlying data is untouched: it stays in UTC and is converted per query.
An unknown name is ignored rather than rejected, so a typo falls back to the
instance default instead of breaking the dashboard. If you serve the API
cross-origin, make sure the header is in `CORS_OPTIONS["allow_headers"]`.

### Virtual datasets that filter in their own SQL

A virtual dataset normally needs to do nothing: Superset converts its temporal
columns and applies the time range on the converted expression, exactly as it
does for a physical table.

That changes when the dataset takes the filter over itself, with
`get_time_filter(..., remove_filter=True)`. The bounds that macro returns are
wall clock in the **display** timezone, while the column is stored in UTC, so
comparing them directly is off by the offset. `remove_filter=True` also means
Superset adds no outer `WHERE` of its own, so nothing corrects it afterwards —
the query silently returns the wrong rows.

Use the `display_time_zone()` macro to convert the bounds back. Do not hard-code
a zone: the macro resolves per request, so a viewer with their own preference,
or an embedded dashboard asserting a zone, still gets the right rows.

```jinja
{% set tf = get_time_filter('created_at', remove_filter=True) %}

WITH bounds AS (
  SELECT
    -- `or "UTC"` makes this an identity when conversion is disabled
    CONVERT_TZ({{ tf.from_expr }}, '{{ display_time_zone() or "UTC" }}', 'UTC') AS start_utc,
    CONVERT_TZ({{ tf.to_expr }},   '{{ display_time_zone() or "UTC" }}', 'UTC') AS end_utc
)
SELECT t.*
FROM events AS t CROSS JOIN bounds AS b
WHERE t.created_at >= b.start_utc
  AND t.created_at <  b.end_utc
```

Converting the two bounds rather than the column keeps the column bare, so
partition pruning and indexes still apply.

Leave the dataset's own temporal column in UTC. Superset converts it again in
the outer query, so converting it here too shifts it twice.

The macro returns `None` when conversion is disabled, and the resolved zone is
already part of the query cache key, so no extra `cache_key_wrapper` call is
needed.

### Resolution order

1. the zone asserted by the request (`?timezone=` or the header above);
2. the current user's own choice (`user_attribute.display_time_zone`);
3. the target database's `Extra`, which may also opt the database out;
4. the `DISPLAY_TIME_ZONE` setting.

Tiers 3 and 4 decide *whether* to convert at all. Neither a request nor a user
preference can enable conversion for a database that opted out, whose data may
not be UTC — they only choose which zone to render in. The resolved zone is part
of the query cache key, so two viewers in different zones never share results.

Setting `DISPLAY_TIME_ZONE = "UTC"` is the useful way to enable the feature
while leaving the choice entirely to each user or embedding host.

## Background

There are four distinct timezone components which relate to Apache Superset,

1. The timezone that the underlying data is encoded in.
2. The timezone of the database engine.
3. The timezone of the Apache Superset backend.
4. The timezone of the Apache Superset client.

where if a temporal field (`DATETIME`, `TIME`, `TIMESTAMP`, etc.) does not explicitly define a timezone it defaults to the underlying timezone of the component.

To help make the problem somewhat tractable—given that Apache Superset has no control on either how the data is ingested (1) or the timezone of the client (4)—from a consistency standpoint it is highly recommended that both (2) and (3) are configured to use the same timezone with a strong preference given to [UTC](https://en.wikipedia.org/wiki/Coordinated_Universal_Time) to ensure temporal fields without an explicit timestamp are not incorrectly coerced into the wrong timezone. Actually Apache Superset currently has implicit assumptions that timestamps are in UTC and thus configuring (3) to a non-UTC timezone could be problematic.

To strive for data consistency (regardless of the timezone of the client) the Apache Superset backend tries to ensure that any timestamp sent to the client has an explicit (or semi-explicit as in the case with [Epoch time](https://en.wikipedia.org/wiki/Unix_time) which is always in reference to UTC) timezone encoded within.

The challenge however lies with the slew of [database engines](/docs/configuration/databases#installing-drivers-in-docker-images) which Apache Superset supports and various inconsistencies between their [Python Database API (DB-API)](https://www.python.org/dev/peps/pep-0249/) implementations combined with the fact that we use [Pandas](https://pandas.pydata.org/) to read SQL into a DataFrame prior to serializing to JSON. Regrettably Pandas ignores the DB-API [type_code](https://www.python.org/dev/peps/pep-0249/#type-objects) relying by default on the underlying Python type returned by the DB-API. Currently only a subset of the supported database engines work correctly with Pandas, i.e., ensuring timestamps without an explicit timestamp are serializd to JSON with the server timezone, thus guaranteeing the client will display timestamps in a consistent manner irrespective of the client's timezone.

For example the following is a comparison of MySQL and Presto,

```python
import pandas as pd
from sqlalchemy import create_engine

pd.read_sql_query(
    sql="SELECT TIMESTAMP('2022-01-01 00:00:00') AS ts",
    con=create_engine("mysql://root@localhost:3360"),
).to_json()

pd.read_sql_query(
    sql="SELECT TIMESTAMP '2022-01-01 00:00:00' AS ts",
    con=create_engine("presto://localhost:8080"),
).to_json()
```

which outputs `{"ts":{"0":1640995200000}}` (which infers the UTC timezone per the Epoch time definition) and `{"ts":{"0":"2022-01-01 00:00:00.000"}}` (without an explicit timezone) respectively and thus are treated differently in JavaScript:

```js
new Date(1640995200000)
> Sat Jan 01 2022 13:00:00 GMT+1300 (New Zealand Daylight Time)

new Date("2022-01-01 00:00:00.000")
> Sat Jan 01 2022 00:00:00 GMT+1300 (New Zealand Daylight Time)
```
